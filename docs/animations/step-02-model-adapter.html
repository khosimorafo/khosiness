Step 2 in context

What this step does

Give the harness one request and response shape for a model, regardless of which provider supplies the answer.

What it builds on

Step 1 supplies a validated unit of work; the harness now needs model text or structured proposals without importing provider-specific objects into its core.

Goal

Swap a deterministic fake for a provider transport without changing the harness-facing interface.

End state

ToolCall, ModelResponse, a ModelAdapter protocol, FakeModel, a callable provider wrapper, and their tests are available. Tool calls remain proposals.

01 / 06

Keep the core provider-neutral

For “Where is the CLI version?”, the harness prepares messages and offered tool descriptions. Its call site depends on generate(messages, tools), not a particular provider SDK.

The adapter boundary separates harness logic from model transport.

Queue a known answer

A FakeModel returns the next queued ModelResponse. No network, credentials, or sampling uncertainty is needed to test the harness-facing contract.

A deterministic fake lets the same input produce a known output.

Inspect what the harness sent

FakeModel.calls retains the exact messages and tool descriptions passed to generate. A test can inspect the request that would have gone to a real provider.

Offered tools are data in the request; their presence is not execution permission.

A tool call is only a proposal

The response can contain a structured ToolCall with an id, name, and arguments. At this stage it is data. Later harness stages validate and authorize it before any runtime acts.

A model response cannot directly read README.md.

Empty queue, explicit failure

When the fake has no queued response, generate raises RuntimeError. The call is recorded before that check, so the attempted request remains inspectable. An event log does not exist yet.

Failure is visible and testable; it is not a fabricated model answer.

Normalize a provider result

CallableProviderAdapter calls an injected transport and validates its dictionary as ModelResponse. Provider-specific conversion belongs behind this boundary; the harness receives the same response type.

Swapping adapters should not change the core response contract.
