01 / 07

Give every fact an envelope

An Event has an ID, run ID, type, UTC timestamp, and payload. These fields identify the record and the run it belongs to. The example describes a task starting; it is not a prompt message.

A factual event records what happened; it does not ask the model what to do.

Append one JSON object per line

JsonlEventStore opens the file in append mode, writes the serialized event plus a newline, and flushes the handle. A reader can inspect the file with an ordinary text editor.

Append new facts; preserve earlier lines and their order.

Reload in the same order

load_all() parses each nonblank line into an Event. The file order is the returned list order. The store does not invent a model summary or choose context.

History is the full sequence; it is not the next model input.

Check a thousand events

A deterministic test appends 1,000 events and reloads them. It checks the count and the last payload index, catching missing, duplicated, or reordered lines in this small checkpoint.

Test the storage behavior before depending on it for recovery.

Inspect after process termination

Once append() returns, the handle has been flushed and closed. A new process can reopen the JSONL file and read that event. This does not promise survival of a machine power loss.

Flush is a process-level check; power-loss durability would need stronger guarantees.

A malformed line fails visibly

If a line is not valid event JSON, load_all() raises a parsing or validation error. The original file remains inspectable, including its earlier good lines. This checkpoint does not repair corruption.

Do not silently turn a damaged history into an apparently complete one.

Keep history separate from context

The event store retains all factual records. A future harness context component will decide which relevant facts a model sees. That selection path is shown conceptually; Step 3 does not implement it.

Store generously; inject selectively.
