Step 4 in context

What this step does

Coordinate one bounded turn at a time: build context, call the model, handle a proposed tool call or final text, update state, and record events.

What it builds on

The Task sets the limit; the model adapter returns proposals; the event store preserves facts. Step 4 connects those separate boundaries.

Goal

Make each transition observable and stop when a final answer or step limit is reached, without an endless hidden conversation.

End state

RunState and a minimal run loop pass tests for a two-turn tool-then-answer path, a first-turn answer, a step limit, and a returned fake-tool failure. Real tools and policy come later.

01 / 07

Start from a bounded task

The Task supplies max_steps; RunState tracks the current step, observations, whether the run has finished, and any final answer. The loop checks both finished and the step budget before each turn.

The harness owns current run state and decides when another turn is allowed.

Build this turn's view

The context builder turns the task and current state into messages. The loop increments the step, records model_called, and asks the provider-neutral model adapter for a response using offered tool schemas.

History is not fed wholesale to the model; the context builder chooses this turn's messages.

The model proposes a tool call

The loop records model_responded and tool_requested. A ToolCall is structured data from the model. In the Step 4 test, an injected FakeTools object handles the call; real tool validation and permission policy arrive later.

A proposal is not general authority to use the outside world.

Act, observe, and save

The injected fake returns a successful result. The loop adds that result to RunState.observations, records tool_completed, and calls save_state. The next turn can then build messages from the updated state.

The observation changes the next turn; the event records the fact durably.

Final text completes the run

On turn two the fake model returns text with no tool calls. The checkpoint loop marks finished, stores final_answer, records task_completed, and saves state. It stops after two turns. Later stages add stronger completion checks against task criteria.

Only the harness changes finished; model text is treated as the candidate answer.

The step limit stops an unfinished run

If the model keeps asking for tools through max_steps, the loop exits with finished still false and emits step_limit_reached. It does not invent a successful final answer.

A bounded failure is an observable outcome, not silent endless work.

A tool error becomes an observation

When the injected tool returns ok=False, the loop records tool_failed and stores the result in observations. The loop can continue on a later turn while the step budget permits. This is a returned failure result, not an exception thrown out of the loop.

Record the failed action so later reasoning can respond to it.
