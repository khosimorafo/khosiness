Step 9 in context

What this step does

Map a harness-classified action to allow, ask, or deny, and request explicit human approval where policy requires it.

What it builds on

The registry dispatches tools and Step 8 plans execution infrastructure. Neither the existence of a tool nor a risk label authorizes a call.

Goal

Place a deterministic authority gate before execution, with exact action details and a factual decision record.

End state

Planned: risk types, PolicyEngine, ApprovalUI, and tests. The reference provides decision helpers; loop integration and decision events must still be implemented and verified.

Conceptual simulation. All approval answers and decision traces are illustrative. Buttons move through scenes; they do not authorize real actions. The current loop has no policy gate. 6. Deny a destructive request

8. Connect the gate before claiming safety
Helpers that return decisions do not stop a loop that never calls them. Stage implementation must connect classification, evaluation, approval, recording, and dispatch. Test that denied or pending requests have zero runtime calls, not merely that a helper returns DENY.
Capability ≠ authority. A policy helper ≠ an enforced policy gate.
