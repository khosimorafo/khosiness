Serialize current run state and reload a validated task and checkpoint after process interruption.

What it builds on

Step 4 owns working RunState and an optional save callback. Step 3 owns factual events; neither automatically reconstructs the other.

Goal

Continue from an explicit saved position, avoid rerunning a finished run, and detect uncertainty before repeating a side effect.

1. Separate three kinds of record
The process holds mutable RunState. The event store holds a factual history. The context builder selects messages for a model call. A checkpoint serializes working state; it does not turn all three into one transcript or automatically reconstruct state from events.
State ≠ history ≠ selected context.

2. Capture a useful position
The planned state adds status, plans, completed_work, pending_actions, and artifacts. These fields describe position but do not execute recovery logic. Persist the task separately so the restart has both its contract and its current state.
A field named completed_work does not prevent duplicate execution.

3. Replace the snapshot atomically
The helper writes a complete temporary JSON file, then replaces state.json with os.replace. Under a single writer on the same filesystem, readers see the previous or the replacement file, rather than a half-written committed JSON document. No fsync is included.
Atomic visibility is not a power-loss durability guarantee.

4. Ignore an interrupted temporary write
Suppose the process stops while writing the next temporary snapshot. state.json still contains the last committed state; a truncated state.json.tmp is not used by load_checkpoint. This assumes interruption before replacement and says nothing about power loss.
Resume from the committed file, not whichever file looks newest.

5. Validate, then resume unfinished work
load_run reads task.json through Task validation and state.json through RunState validation. resume_run passes an unfinished state to the injected runner. The runner and supplied dependencies must continue from that position; the helper does not replay the event log.
Loading JSON is only the beginning of a recovery contract.

6. Return a finished run without rerunning
The helper checks state.finished after loading. If true, it returns the saved state without invoking the runner. This avoids rerunning this completed run, but it does not prove that the original final answer met the success criteria.
Finished means accepted final text in the current loop, not verified task success.

7. Stop at an uncertain side effect
A write can succeed just before a crash prevents checkpointing its result. The old checkpoint then cannot tell whether the action happened. Repeating it blindly risks a duplicate effect; atomic snapshot replacement does not close this gap.
Reconcile evidence or use an idempotency protocol before retrying.

8. Reject unusable committed state
A malformed committed state.json fails Pydantic validation. Missing files and invalid task workspaces can also stop loading. The reference propagates these errors; it does not silently return to step zero or claim a successful recovery. Preserve evidence and diagnose before continuing.
Recovery must expose uncertainty, not invent continuity.
