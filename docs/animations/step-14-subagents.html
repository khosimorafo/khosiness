What this step does

Give a child an explicit objective and return a structured result instead of sharing an entire transcript.

What it builds on

The core loop and tool boundaries can support a separately configured child; skills supply procedures, not new authority.

Goal

Gain context isolation while keeping child tools, steps, and evidence under harness control.

End state

Planned: AgentRequest, AgentResult, and spawner. The reference forwards requests and checks IDs; child runtime enforcement must be supplied.

Conceptual simulation. Every example, output, and trace is illustrative. This page performs no harness tool execution, storage, delegation, grading, or personal profiling. Planned mechanisms are separate from the current implementation; use STAGE_TRACKER.md for actual progress.

1. Delegate a bounded question
The parent needs to know which caller uses a retry setting. A child request can narrow that question while the parent retains the wider task. Delegation should isolate a useful subproblem, not merely assign a persona.

2. Carry tools and a step budget
The request names allowed_tools and max_steps. Those are requirements for the child runner to enforce. Merely storing read_file and five steps in a Pydantic object cannot stop an unrestricted injected function.
A declared limit needs an enforcement point.

6. Reject a mismatched result ID
The spawner checks the returned child_run_id against the one it generated. A wrong ID raises ValueError. This prevents accepting a handoff labeled as a different invocation; it does not verify the factual correctness of its evidence.
Identity validation and evidence verification are distinct.
