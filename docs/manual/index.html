khosiness — Harness Engineering From Scratch

A first-principles build manual for constructing khosiness: a deeply personal agentic operating harness for one software engineer. Phase I builds the substrate; Part II evolves it into a continuously improving extension of the engineer. The shorthand/CLI name is kness.

Preface · Before the first step

Why LLMs make agents possible

A large language model (LLM) can translate a goal and the evidence available into a proposed next action. Put that capability inside a program that executes permitted actions, supplies their results, and repeats under limits, and you have the foundation of an agent.

What the model brings

A language model generates tokens—pieces of text—conditioned on its input. Training on language and code gives it reusable patterns; additional training can improve how it follows instructions. This lets us describe work in ordinary language instead of writing a separate decision tree for every request. It still makes mistakes. Research: instruction following.

Interpret a request

Turn “find where this CLI gets its version” into candidate steps such as locating the command, reading its imports, and following a definition.

Use supplied context

Read instructions, code, examples, and observations together. A newly supplied file can inform the answer without retraining the model.

Propose structured actions

Tool-capable models can select a named operation and supply arguments in a machine-readable format. Support and reliability vary by model.

Adapt after feedback

Use a search result or error to revise the next proposal. Repeated calls make it possible to investigate a task whose exact path was not known beforehand.

Interleaving model decisions with observations is the central idea explored by ReAct. The program must arrange that feedback loop; a model response alone does not keep a task running.

Tool calling: from a proposal to an operation

A tool is an implemented operation, such as reading a file or searching a repository. The model receives its name, description, and argument schema—the allowed input shape. A tool call is the model's request to use it. The request does not execute itself. Reference: tool-use mechanics.

  1. Task: find the package version and cite its definition.
  2. Model proposal: request read_file with {"path": "src/khosiness/__init__.py"} after locating that file.
  3. Harness decision: validate the arguments and check that this path and operation are permitted.
  4. Runtime action: read the file; return its contents or an explicit error. The harness records the outcome.
  5. Next turn: include the relevant result in context so the model can answer with evidence or propose another lookup.

If the path is outside the permitted workspace, reject it before reading. Valid JSON establishes an input shape; it does not establish permission or correctness. This is a conceptual example: the manual builds tools and policy in later steps.

What makes the whole system an agent?

Here, an agent is a goal-directed system that uses model proposals and environmental feedback to choose its next actions. A fixed workflow follows predefined branches; an agent can choose a route as evidence arrives. Both rely on ordinary software to execute and enforce limits. Reference: workflows and agents.

The harness owns the task contract, visible context, validation, permission checks, execution dispatch, state, history, and stopping rules. A model saying “done” is a candidate result; the harness decides completion against the task's criteria. The early loop is deliberately minimal; later stages strengthen its controls.

Subagents: delegate a bounded piece of work

A subagent is a separate agent run given a narrower task, selected context, tools, and limits. It can use the same model as its parent. For example, one child traces the CLI entry point while another checks version tests; the parent combines their evidence.

Separate contexts keep investigations focused, and independent work can run in parallel. Delegation adds cost and coordination, and the parent must assess returned claims. Context separation alone does not isolate filesystem access; the runtime and policy must enforce that. Example: a multi-agent research system.

Why we are building a harness

The model supplies adaptable proposals. Our software supplies accountable execution. We explicitly store history, select context, preserve state, and later retrieve cross-run memory. Supplying new context does not itself update model weights. Tests and evaluations tell us whether the combined system actually meets its task.

The governing rule: the model proposes; khosiness controls. The following steps build each responsibility until that rule is visible in code, tests, and traces.

How to use the khosiness manual

Phase I takes you from an empty Python repository to a measurable, recoverable agent harness. Work through it in order. Do not advance because the prose is finished; advance when the stage's code checkpoint, tests, trace inspection and exit criteria are all true.

Learning rule: type the important code yourself. The objective is to understand the mechanism well enough that you can later recognize it inside Codex, Claude Code, OpenHands, LangGraph or another harness.
Project identity: the project and harness are named khosiness; the shorthand and command name is kness.
