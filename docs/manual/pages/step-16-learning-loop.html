Understand the step first

Read these four anchors before following the implementation sequence.

What this step does

Turn a repeated failure into one hypothesis, change one harness variable, and rerun the fixed evaluation.

What it builds on

Step 15 provides measurements; without them, a learning loop would confuse plausible changes with proven improvements.

Goal

Improve the harness through controlled experiments whose results can be challenged and repeated.

End state

An experiment record and decision note show the hypothesis, change, measured outcome, and next decision.

Conceptual objective

Use repeated failures to form one hypothesis, change one system variable, and measure the result.

This stage turns the harness into an engineering system: measurable, comparable and improvable through controlled experiments rather than intuition.

# EXP-004: ADR discovery

Observation: 6/15 architecture tasks failed because docs/adr was never found.
Hypothesis: injecting an ADR index will improve architecture-task success.
Change: add ADR discovery during repository initialization.
Constants: same model, tasks, max_steps and tools.
Result: baseline 9/15; variant 13/15.
Decision: keep; investigate remaining failures separately.

Tests to perform

  1. Baseline and variant use the same benchmark.
  2. Run repeated trials if model variance is material.
  3. Check secondary costs such as tokens/tool calls, not only success.
Deliberate-failure rule: after the happy path works, deliberately trigger at least one failure and inspect the returned result, state change and event trace.

What to inspect before moving on

  • The component has one clear responsibility.
  • Failure is explicit and testable.
  • The event log shows the important transition.
  • No provider/framework object has leaked across an architectural boundary without a reason.
  • You can explain what problem this step solves without reading the code.

# Harness experiments

Every harness change that claims to improve reliability should be recorded as
a controlled experiment.

## Required structure

1. Observation
2. Failure class
3. Hypothesis
4. One changed variable
5. Constants held fixed
6. Benchmark result
7. Secondary costs
8. Decision: keep, revert or refine

Do not change the model, prompt, tools and memory policy in one experiment.

# EXP-001 — ADR discovery

## Observation

Several architecture tasks failed because the agent never discovered
`docs/adr/`.

## Failure class

Missing context caused by weak repository discovery.

## Hypothesis

Providing an ADR index during repository initialization will improve
architecture-task success.

## Change

Add ADR discovery to repository initialization.

## Constants

- same model;
- same benchmark set;
- same step limit;
- same tool set.

## Result

Baseline: 9 / 15 successful.

Variant: 13 / 15 successful.

## Decision

Keep the change.

The remaining failures should be inspected before another harness variable
is changed.
Do not advance until this passes
